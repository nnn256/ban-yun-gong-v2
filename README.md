# 搬运工 V2

在 Windows 本机按规则转发 QQ 和飞书消息。支持 QQ→QQ、QQ→飞书、飞书→QQ、飞书→飞书，可逐条选择转发的账号、会话和内容类型，无需配置 AI。

## 下载与安装

- [下载 2.0.15 中文安装包（Windows 10/11 x64）](https://github.com/nnn256/ban-yun-gong-v2/releases/download/v2.0.15/MoverV2-Setup-2.0.15-x64.exe)
- [下载 2.0.15 便携 ZIP](https://github.com/nnn256/ban-yun-gong-v2/releases/download/v2.0.15/MoverV2-2.0.15.zip)
- [发行说明与 SHA-256 校验文件](https://github.com/nnn256/ban-yun-gong-v2/releases/tag/v2.0.15)

1. 双击安装包，按中文向导完成安装。默认目录是 `%LOCALAPPDATA%\Programs\搬运工V2`。覆盖升级时，在“选项”选择原安装目录，以便沿用本机登录、群映射和设置。
2. 点“启动工作台”，以后可双击桌面“搬运工V2工作台”，也可从开始菜单打开。首次启动需要联网准备 Python、AstrBot 和平台连接组件，无需手动安装开发环境。新安装会在默认工作台端口 `18766` 被占用时从 `18767`–`18786` 选择空闲端口，浏览器会打开实际地址。
3. 在“接入向导”扫码，并按提示完成 QQ 协议确认。到“群映射”自行选择来源和目标。全新安装从空规则开始。运行总览应显示桥接插件 `v2.0.15` 和“桥接版本已核对”。

便携版请完整解压 ZIP，双击 `打开工作台.vbs`。若只需在后台运行，可双击 `搬运工V2.exe`。安装包和 ZIP 均不携带 QQ 或飞书会话、真实规则、群映射、运行日志和聊天数据。

卸载前可在“本地设置 → 后台保活”关闭 Windows 登录后自动运行，再运行安装目录中的 `stop-workbench.ps1` 停止当前实例。在 Windows **设置 → 应用 → 已安装的应用** 找到 **搬运工V2 安装程序**，选择**卸载**。程序文件及快捷方式由 Windows 安装器移除，本机配置和 `runtime` 数据可留给下次安装使用。

## 2.0.15 发送权限与回执修复

2026-11-22：处理“QQ 和飞书都在线，但飞书转 QQ 持续失败”的诊断。

- 在线与可发送分别核对。SnowLuma 的 `/api/status` 在协议确认和初始密码限制下仍可返回在线，因此工作台额外核对协议和认证状态。
- 尚未满足发送条件时，待处理飞书消息保存在本地，不消耗有限的发送重试次数。已耗尽次数的旧失败记录仍需在工作台点击“重试失败消息”。不自动重发回执不明的消息。
- 已在 SnowLuma 扩展明确开启“自动确认协议”的用户可沿用该本机设置。新安装仍由使用者阅读协议并选择是否启用。
- 忽略已完成、已取消请求的重复或迟到 OneBot 回执，避免 `InvalidStateError` 打断反向 WebSocket。
- 合并短时间内的 QQ 状态查询，减少逐图发送触发的重复账号和群列表查询。
- QQ 发送拒绝日志增加固定错误码和 HTTP 状态，不记录令牌、消息正文或接口原始错误正文。
- 会话列表写入使用独立临时文件，并发写入时避免共享临时文件冲突。

工作台 QQ 连接区域会显示实际发送权限。安装进度和启动错误可从安装目录的 `runtime\logs` 查看。

仅显示器息屏可继续后台运行；Windows 系统睡眠时无法执行本地程序，醒来后由现有持久收件与补读流程恢复。不把防空闲睡眠请求描述成可在真正睡眠中实时收发。

发送权限专项覆盖协议确认、回执去重、权限恢复和跨平台独立转发。详细验证范围见 [VERIFICATION.txt](VERIFICATION.txt)。

## 2.0.14 连续单图、断线补收与飞书表情

- **连续单图和断线。** 已启用的飞书群映射首次建立补收起点，连接期间约每 20 秒核对一次，重连后立即检查。消息和读取进度保存到本机队列，补收与实时推送去重，未读到的缺口保留待查。修改群映射会重新建立起点，上一条规则下的补收结果不会发送到新目标。工作台 **运行总览 → 平台连接** 可看补读起点、入队数量和待核对缺口。
- **真实图片与表情。** 一条富文本内的多张图片仍按原顺序发送；截断预览等补全后再发。普通消息、富文本和合并聊天记录内的常见飞书表情转成对应的可见符号，重复表情保留，各条映射的文字和表情开关分别生效。贴纸有可读图片资源时走图片传输，飞书与 QQ 的表情外观可能不同。
- **定位漏发。** 转发日志可分别核对图片是否写入收件队列、是否匹配规则、QQ 发送接口是否接受。查看失败和回执不明的记录时，先核对目标群，再决定是否补发。

只关闭显示器时，保持 Windows 用户登录、网络和转发服务在线即可继续运行。在 **本地设置 → 后台保活** 开启后台自动恢复和防空闲睡眠，确认页面显示防睡眠请求已生效。电脑实际睡眠时无法实时转发；唤醒后可补收已有起点且飞书仍可读取的消息。新版不会重放起点之前的历史，也无法恢复平台未返回的图片。

## 2.0.13 飞书系统通知过滤及桥接插件升级

修复飞书的系统通知被转发到 QQ 为 `[系统消息] type=9` 的问题。固定 LarkAgentX 会为通知生成这段摘要，旧插件将摘要当作聊天文字发送。新版按飞书消息类型过滤，覆盖实时推送、批量与 SID 补拉、旧队列恢复和合并记录内的通知。群成员正常输入的同样字样仍可转发。

本版保留同条多图、截断补读和后台保活。飞书带截断标记的消息只补读同一条可见消息，正文完整后再按顺序发送图片；若补读后仍截断，保留重试。QQ 同一条消息内可包含多张真实图片，具体排版由 QQ 客户端决定。

本节为历史修复说明，2.0.14 保留这些改动。只更新文件或看到工作台版本变更，不能证明 AstrBot 已加载新插件。若显示代码不一致，按页面提示安装桥接插件并重启 AstrBot，再刷新核对。

本版不自动补发旧 QQ 群历史。QQ 聊天窗口仍能看到历史语音，也不能据此确认 OneBot 可以取到并重新发送那条语音。已发送的系统摘要不会自动撤回；旧版已遗漏且未保存的媒体需要手动重发。

## 2.0.12 飞书同条多图、截断补读与发送回执修复

本版针对“飞书一条消息叠放五张图片，QQ 却显示 `[富文本][图片]` 或缺图”的问题修复实际解析和发送流程。固定 LarkAgentX 的 POST 包含 `richText` 和 `richTextWithMd` 两种表示；旧代码仅使用前者。现在优先读取有效的非空 Md 表示，保留原始图片顺序；有效空 Md 才回落旧表示，不拼接两棵树，也不把损坏正文降级为摘要后记作成功。不能仅凭截图认定某一条历史消息的原始节点类型。

- **真实多图发送。** 普通富文本中的连续图片会下载并校验实际内容，再组成 QQ 同一条消息的多个图片段。五张普通大小图片在一组发送；本项目按最多 8 张或约 16 MiB 原始图片数据拆组，合法的大单图独立处理。这是本地资源策略，非平台官方上限。文字、视频及真正合并记录的原始边界会保留。
- **截断消息先补全。** 推送、批量和 SID 补拉均保留 `isTruncated`。发现正文或合并记录子消息截断时，只补读当前可见消息 ID，核对消息、会话、发送人和当前账号；完整正文先保存再发送。补读缺失、仍截断或身份不符时保留重试，不把预览当全部内容。普通引用标识不会触发扩读历史。
- **Markdown 图片有明确支持范围。** `MARKDOWN` 节点支持标准 inline `![说明](引用)`，引用须精确对应当前消息内图片资源别名或 `imageKey`，按正文顺序展开。未知或不支持的图片结构会明确失败，避免假装纯文字发送成功；不会下载任意外部网址或追加正文未引用的缓存图片。
- **失败只补未成功内容。** 一张图片下载明确失败后仍处理其余图片，恢复时只补该图。QQ 已接受但本地回执存储暂时失败时，只重试保存回执；明确拒绝后则等待释放本地预留，避免误判成功。超时等未知回执保留不确定状态，需要核对目标，不拆图盲目重发。
- **合并记录兼容。** 兼容 OneBot 标准 `get_forward_msg.message` 和旧实现的 `messages`；跳过已删除子消息，尚未补全的子消息不能转发摘要。真正合并聊天记录仍按子内容转发，本版不保证跨平台原生引用卡片和飞书客户端排版完全相同。

上述修复已并入 2.0.13。按下方步骤升级后，可以在原映射的飞书群发送一条含五张图的新消息，检查 QQ 端是否收到顺序正确的五张图。只复制 EXE 无法更新插件代码，EXE 默认后台运行，打开页面请使用 `打开工作台.vbs`。

包内不含 QQ / 飞书登录数据、群映射、工作规则、运行收件箱或聊天附件。旧版已发出的 `[富文本][图片]` 不会自动替换，未保存的历史图片不能凭空恢复；需人工重发原消息，或对已保留的失败收件使用工作台重试。测试使用合成协议、临时数据库和模拟外部发送，没有在提供日志的电脑完成真实账号收发验收。

协议来源、实现依据和边界见 [PROTOCOL_REVIEW.md](PROTOCOL_REVIEW.md)，完整验证结果见 [VERIFICATION.txt](VERIFICATION.txt)。2.0.11 的后台保活修复和既有四方向转发功能全部保留。

## 2.0.11 息屏与后台保活修复

仅关闭显示器不应暂停转发。旧版存在守护启动后尚未产生心跳就报告成功，以及 AstrBot 启动中途出错后没有启动守护的路径，可能出现工作台还在运行、防空闲睡眠却未生效的情况。本版等待本安装守护的真实心跳，提前启动守护，并修复更新后启动失败时的守护恢复；直接启动工作台 Python 也会初始化守护，保留用户已有开关和端口。

同时修复安装暂停标记在 Windows PowerShell 5.1 下的时区偏差、保存后台设置时自定义端口被改回默认值，以及手动停止 AstrBot 与自动恢复同时发生时又被启动的问题。安装启动和守护恢复分别处理，关闭开关或手动停止会保留。

在 **本地设置 → 后台保活** 开启“启用后台自动恢复”和“运行期间阻止系统空闲睡眠（允许息屏）”，点击“保存后台设置”。等待显示 **“防空闲睡眠请求已生效，允许显示器关闭”**，再关闭显示器。页面会分别报告守护未运行、心跳无响应、防睡眠请求失败或已关闭；失败时导出工作台诊断 ZIP，可查看 `supervisor` 日志。

请区分关闭显示器与电脑睡眠。电源键、开始菜单“睡眠”、合盖、休眠或退出 Windows 用户可能暂停或结束进程，防空闲睡眠请求不能保证阻止这些手动操作。请在 Windows“设置 → 系统 → 电源和电池 → 屏幕、睡眠和休眠超时”中分别设置屏幕关闭和睡眠；接电运行时可让屏幕按时关闭、设备睡眠设为“从不”，但本程序不会自行修改系统电源方案。只有转发进程和网络继续运行时才能实时收发；显示器关闭或锁屏的实际行为还需在发生问题的电脑上验证。

本节为 2.0.11 历史修复说明。当前安装包仍不包含登录数据、群映射和工作规则。

已有日志未包含发生问题那台电脑的电源事件或守护日志，无法据此证明当时进入了睡眠。本版修复已确认的启动和状态判断缺陷，不将其描述为那次息屏停转发的唯一原因。未在用户电脑执行强制息屏、锁屏或睡眠测试。

## 2.0.10 图片连续发送、失败恢复与诊断修复

本版针对飞书连续发送多张图片时的接收、下载和逐项发送流程增加持久收件箱，并修复中间一项失败后跳过后续内容、批量读取不完整以及日志导出仅有当前页的问题。修复依据为代码检查和离线故障回归；目前没有在提供日志的那台电脑完成新版真实群收发测试，不能据此承诺零漏发或认定旧版 18:45 漏图的唯一原因。

- **先保存收件，再处理媒体。** 飞书推送及需要补读的消息 ID 先写入本机 SQLite 收件箱，再由 3 个处理任务读取、下载和转发，避免一张慢图阻塞整个接收流程。发往 QQ 的实际发送仍然串行。慢图恢复后可能晚于后续已就绪的图片到达，不承诺跨消息始终保持原发送顺序。
- **一项失败，后续继续。** 富文本、合并记录按内容片段分别解析、筛选和记录发送结果。离线回归包含连续 30 张图、中间一张失败的场景：其余 29 张继续发送，恢复后只补失败的那一张，已确认成功的片段跳过。
- **重试和重启恢复。** 临时下载或明确发送失败采用有限次数的延迟重试；用尽后保留失败项。AstrBot 重启后，已落盘但未完成的收件会继续处理；按飞书账号及实际登录用户隔离，切换账号不会把原账号的待处理消息用新账号发出。
- **回执不明先核对。** 请求已经发出却没拿到可确认的发送回执时，会保留“不确定”记录。系统不会盲目自动重发；先去目标群核对是否收到，再决定是否人工重新发送。工作台“重试失败消息”也不会清除成功或不确定的发送收据。
- **工作台可查看与重试。** “运行总览”显示飞书收件的待处理、处理中、重试用尽数量，以及正在发送或回执不明的数量。“重试失败消息”只将重试用尽的失败项重新排队，不改动正在处理或已完成的收件；重复点击有防护，完成后刷新状态。没有失败、服务未运行、飞书监听未连接或队列不可读时，按钮不可用。
- **诊断日志可追踪。** 修复 AstrBot / Loguru 日志缺少 `plugin_tag` 时的兼容问题；新增不含正文和资源 URL 的重试、发送结果等结构化事件。导出改为各组件当前仍保留的日志 ZIP，包含轮转文件，不再受工作台当前 1000 条或筛选条件限制。

持久恢复只覆盖 **2.0.10 及以后版本已成功写入本机收件箱的新收件**，需要保留原安装的运行数据。升级不会自动重放旧群历史，无法凭空补回旧版 18:45 已经漏掉、也未被保存的图片；需要补发历史内容时，请在目标群核对后人工重新发送原消息。

### 把新版发到出问题的电脑升级

1. 运行 [最新 Windows 安装包](https://github.com/nnn256/ban-yun-gong-v2/releases/latest)。在向导的“选项”核对原安装目录，安装前停止旧版后台。保留该目录的 `runtime`、本机设置和规则。
2. 安装完成点击 **启动工作台**，也可以双击桌面 **搬运工V2工作台**。首次准备运行环境时需保持联网；有本机数据的原目录会沿用原配置。
3. 浏览器打开后，确认 **运行总览 → AstrBot 本地实例** 显示 **桥接版本已核对**，且版本和安装包相同。然后检查 QQ 的 OneBot 连接、飞书监听、映射方向和补读起点。
4. 在测试会话检查连续单图、同条多图、合并记录内表情、语音和视频，观察目标群和工作台队列。若“重试用尽”增加，恢复网络或平台连接后点击“重试失败消息”；若显示回执不明，先核对目标会话。

`搬运工V2.exe` 默认只启动后台，**不会自动弹出浏览器**。需要查看页面时运行 `打开工作台.vbs`，或在后台已启动后访问 `http://127.0.0.1:18766/`。首次安装需要联网下载 Python / AstrBot / LarkAgentX / SnowLuma 等运行组件，消息转发也依赖平台网络；本项目是本机部署，不是完全离线软件。QQ 与飞书重新登录、扫码和必要的协议确认需要本人完成。

全新安装按“接入向导”登录并在“群映射”选择来源、目标和内容类型。发行包不包含任何人的 QQ / 飞书登录数据、群映射、工作规则、收件箱或消息附件；升级保留的数据来自接收方电脑的原安装。

### 发生异常时导出诊断

在工作台“实时日志与查询”点击 **“导出诊断日志 ZIP”**，保留 ZIP 内的 `manifest.json`。默认导出预算为每个日志文件最多 16 MiB、合计 128 MiB、最多 240 个文件，优先保留转发相关证据。超过预算时导出日志末尾，清单会标记 `truncated`、`skipped_limit` 或 `unavailable`；`complete=false` 表示发现的文件没有全部导出。即使 `complete=true`，也只代表发现且仍保留的日志范围，不代表平台完整聊天历史；已被上游删除或轮转清理的记录无法恢复。

诊断 ZIP 不包含登录文件、配置、规则、SQLite 收件箱或聊天附件。日志会隐藏常见凭据字段和资源链接，但 AstrBot、SnowLuma 等上游原始日志仍可能记录聊天正文、群号或用户信息；发送给他人前请先检查内容。

## 2.0.9 修复 Windows PowerShell 5.1 更新

如果更新时出现 `NameError: name 'update' is not defined`，完整解压新版 ZIP 到新文件夹，然后双击 `打开工作台.vbs`。新版会先定位正在运行的工作台，安全退出旧进程后再更新原目录，保留本机映射、登录和后台设置。新版启动后，再到「本地设置 → 后台保活」保存。即使自动恢复已关闭，也可以手动打开工作台。

## 2.0.8 原生视频与映射编辑

已保存的规则可以在编辑窗口改为单向或双向。改为单向只移除对应的反向规则。列表里的“转发本人：开/关”会立即保存当前方向；这个开关仍默认为关闭。升级同时修复了 QQ 账号专用配置覆盖全局本人消息上报的问题。开启映射的本人开关后可以转发本人手动发送的新消息，程序自己的转发回声仍会过滤。

飞书富文本或合并记录内的视频会提取真实视频内容。发到飞书使用原生视频消息，发到 QQ 使用原生视频段。合并记录中的文字和图片按原顺序转发，省去合并标题、发送者编号和资源标识。媒体读取或发送失败会写入转发日志。旧版已发出的摘要不会自动替换，请重新发送原消息测试。

## 2.0.7 本人消息与隐藏后台

本人消息开关仍默认关闭，在每条映射的“转发本人手动发送的消息”中单独开启。本版补上 QQ 节点本人事件上报，并修复本人向好友发消息时被错误归入本账号会话的问题。关闭时不转本人消息，打开后转发，重复上报和程序自己的转发回声仍会被过滤。升级只修改本项目的 QQ WS 节点，不会替你打开规则开关。

`后台运行.vbs` 完全不创建命令窗口；`一键启动.cmd` / `更新并启动.cmd` 会立即转交无窗口 EXE 后退出，CMD 本身可能短暂闪现。后台入口不自动打开浏览器和接入向导；启动失败写日志，避免弹框打断无人值守。`打开工作台.vbs` 明确打开浏览器，后台保活继续工作。安装版开始菜单分别提供“后台运行搬运工V2”和“打开搬运工V2工作台”；桌面的工作台快捷方式打开设置页面。QQ/飞书的扫码或重新登录仍需人工完成，平台登录窗口按需显示；保持会话在线即可，无需一直打开工作台页面。

更新时完整解压新版 ZIP，双击 **一键启动.cmd** 或 **更新并启动.cmd**。程序先校验新版每个文件的 SHA-256，再自动定位已登记或正在运行的旧安装目录，只覆盖程序文件；`runtime`、QQ/飞书登录信息、转发规则和本机设置保持原样。旧程序文件备份保存在原目录的 `runtime/update-backups`；覆盖失败会回滚。若旧安装已被删除，新包不能恢复此前已删除的登录数据，需要重新扫码。开发目录没有发行清单时可本地启动，跨目录更新必须提供完整校验清单。

一键启动后，工作台与 AstrBot 在后台运行，并由守护进程在异常退出后自动恢复。SnowLuma 原生连接器在已启动后意外退出时也会按退避策略恢复；手动停止和等待扫码会被保留。飞书连接随 AstrBot 加载已有凭证恢复，凭证失效时需重新扫码。在“本地设置 → 后台保活”中，可分别设置自动恢复、防空闲睡眠与 **Windows 登录后自动运行**。关闭浏览器、锁屏或仅关闭显示器通常不会停止后台进程；须确认防空闲睡眠请求实际生效，并保持电脑联网、Windows 用户已登录。手动睡眠、休眠、关机及退出用户会中断转发。

“运行总览 → 实时日志与查询”可以按组件、级别、关键词、时间和日志文件筛选，并查看更早记录。覆盖 AstrBot、SnowLuma、飞书连接、转发插件、后台守护、工作台与启动配置；实时刷新可随时关闭。新产生的工作台、守护、转发和 AstrBot 收集日志按大小轮转；查询结果会隐藏常见凭证字段。

本版还修复普通文本信封内嵌富文本视频的解析，覆盖本人消息与 QQ 私聊。无效媒体会记录失败，不会把 `[富文本] [视频]` 摘要当正文发送。旧版已经发出的占位文字属于历史消息，需要重新转发。

发布包包含固定版本 SnowLuma Go 插件源码归档，来源、提交、校验值和许可证见 `vendor/snowluma-go.json` 及归档内 `LICENSE`；SnowLuma 本体首次启动按官方发布包 SHA-256 校验后下载。LarkAgentX 的完整扫码依赖同时按 AstrBot 宿主版本校验，避免首次扫码缺包。

搬运工V2 包含独立运行的本地工作台和 AstrBot 插件。每条映射可以独立选择 QQ 或飞书作为来源和目标，因此支持 QQ→QQ、QQ→飞书、飞书→QQ、飞书→飞书，也支持一个来源转发到多个目标。LarkAgentX 的 agent backend 固定为 `none`，桥接插件会截住受管平台事件，不触发 AstrBot AI 回复。

## 从源码运行

在 Windows PowerShell 中运行：

~~~powershell
Set-ExecutionPolicy -Scope Process Bypass
.\start-workbench.ps1
~~~

首次运行会在 `runtime` 下准备 AstrBot 4.29.4、固定提交的飞书连接组件和桥接插件。启动日志显示实际工作台地址。AstrBot 管理页默认使用 `http://127.0.0.1:6185/`。首次密码会显示在工作台。登录并按提示修改后，把新密码粘贴回工作台保存，密码副本使用 Windows DPAPI 加密。

在“群映射”中分别选择来源和目标平台、账号、会话类型与群/好友；支持 QQ→QQ、QQ→飞书、飞书→QQ、飞书→飞书。同一来源也可配置多个目标。选择双向会创建两条独立映射。每个 QQ 账号分别显示登录与 OneBot 状态，群归属由已验证的群列表确认。会话选择器优先显示经元数据核验的群名或联系人名，并保留会话 ID。本人手动消息默认关闭，可在新建规则时勾选或在已保存的规则表逐条切换；顶栏全局开关可暂停或恢复所有映射。桥接回声按发送回执过滤。LarkAgentX 扫码凭证存放在 `runtime\LarkAgentX-data`。工作台启动时会下载固定提交的源码包并校验 SHA-256，然后仅安装它运行时缺少的 protobuf 依赖。

AstrBot OneBot v11 反向 WebSocket 实例使用本机地址 `127.0.0.1`、端口 `6199`，OneBot Access Token 留空。LarkAgentX 用飞书 App 扫码登录个人账号，不需要创建飞书机器人 App ID / App Secret；其凭证仅保存在本机数据目录。

停止 AstrBot 使用工作台按钮，守护进程会尊重手动停止。停止本安装的工作台与 AstrBot 运行 `.\stop-workbench.ps1`；本机登录和规则会保留。只关闭浏览器标签不会停止后台运行。

本地安装 AstrBot 与插件也可单独运行 `.\install_astrbot.ps1`。打包项目运行 `.\package.ps1`；ZIP 不包含 AstrBot 虚拟环境、运行日志或本地平台数据。

## 本机部署

1. 运行 `.\start-workbench.ps1`，打开 AstrBot 管理页，首次登录后设置新密码。
2. 桥接插件只处理规则转发；无需配置大模型。
3. 在“机器人”添加 OneBot v11，ID `qq_bridge`，主机 `127.0.0.1`，端口 `6199`，Token 留空，保存。
4. 在“扩展功能 → SnowLuma 控制台”按“部署步骤”安装并启动 SnowLuma；阅读后手动确认用户协议/隐私政策，启动 QQ、扫码登录，再在“节点配置 → WS 客户端”添加 AstrBot 地址 `ws://127.0.0.1:6199/ws`，端口 6199，Token 留空。
5. 在 SnowLuma 扩展页点“同步连接”，确认在线状态。
6. 在工作台“接入向导”生成飞书二维码，用飞书 App 扫码登录个人账号。LarkAgentX 凭证写入本机 `runtime\LarkAgentX-data`；LarkAgentX agent backend 固定为 `none`。
7. 在“群映射”分别选择来源和目标，可建立 QQ→QQ、QQ→飞书、飞书→QQ 或飞书→飞书；选择双向可自动生成反方向规则。本人消息默认关闭，可在新增映射时勾选或在规则表逐条切换。顶栏“停止全部转发”会暂停所有映射但保持监听；点击“恢复全部转发”可重新开始。
8. “打开本机 QQ 扫码”会复用当前 Windows QQ 客户端；如果账号尚未登录，请在 QQ 窗口用手机 QQ 扫码。本机飞书桌面客户端可单独打开用于查看；消息监听状态以 LarkAgentX 连接和工作台实时状态为准。

若需手动安装插件到另一 AstrBot 根目录，运行：

~~~powershell
Set-ExecutionPolicy -Scope Process Bypass
.\install.ps1 -AstrBotRoot 'D:\AstrBot'
~~~

规则文件位于：

~~~text
<AstrBot根目录>\data\plugin_data\astrbot_plugin_message_bridge\bridge_rules.json
~~~

工作台保存后，下一条消息会使用新映射；顶栏全局开关即时暂停或恢复转发。修改插件代码后需重载插件或重启 AstrBot。

## 配置规则

每条规则的 `source_platform` 可为 `aiocqhttp` 或 `larkx`，目标也可为这两个平台，因此覆盖四种组合。QQ 的 `source_platform_id` 使用 OneBot 实例 ID；LarkAgentX 账号 ID 固定为 `default`。QQ 目标 UMO 为 `qq_bridge:GroupMessage:群号` 或 `qq_bridge:FriendMessage:好友QQ号`；飞书目标为 `larkx:GroupMessage:chat_id` 或 `larkx:FriendMessage:chat_id`。通过 `source_account_id` 和 `target_account_id` 指定 QQ 账号。`include_self` 控制是否转发本人手动发送的消息，默认 `false`；顶层 `bridge_enabled` 控制所有规则的全局暂停与恢复。

例如：

~~~json
{
  "name": "QQ 群转飞书群",
  "enabled": true,
  "source_platform": "aiocqhttp",
  "source_platform_id": "qq_bridge",
  "source_message_type": "GroupMessage",
  "source_session_id": "123456789",
  "target_umo": "larkx:GroupMessage:FEISHU_CHAT_ID"
}
~~~

飞书群反向到 QQ 时来源平台设为 `larkx`、实例 ID `default`，来源会话填写对应 `chat_id`，目标会话填 `qq_bridge:GroupMessage:QQ群号`。首条飞书消息会把会话 ID 记录在工作台可选列表中。样例文件在插件目录的 `bridge_rules.example.json`。

每条映射可分别勾选文字、表情包、图片、视频、语音和文件；“编辑”可修改现有单向或双向映射。旧映射未设置 `content_types` 时默认允许全部类型，禁止空选择。本人手动消息由 `include_self` 控制，默认关闭；桥接自己发送的消息按回执过滤，始终防止回声循环。

飞书视频同时支持独立 MEDIA 消息和嵌在 POST 富文本中的视频。富文本与合并记录按元素顺序解析真实文字、图片和媒体资源，各节点分别经过类型筛选；视频不再变成 `[富文本] [视频]` 摘要。缺少资源或下载失败会记录失败，不把内部媒体占位符当正文发送。无论目标是 QQ 还是飞书，也无论是否允许全部类型，这两类消息都按内容片段解析和发送；不承诺保留原富文本卡片的排版。

转发文字只保留正文。图片和 QQ 数字表情按图片发送，表情包单独筛选。QQ→飞书语音转换为 Opus 并发送原生 AUDIO；视频转换为 H.264/AAC MP4、提取封面并发送原生 MEDIA。飞书→QQ先下载实际媒体，再使用 SnowLuma 管理器的 Record、Video 原生消息段；飞书→飞书按消息类型使用原生媒体接口，富文本与合并记录仍逐片段发送。音视频发送不会自动降级为普通文件；错误会计入失败，已发送成功的消息片段在重试时不重复发送。本轮通过离线测试核验 AUDIO=7、MEDIA=15 请求序列化、QQ record/video 回执处理及媒体下载分支，没有进行真实平台发送；实际送达与播放需升级后在授权测试会话核对。首装脚本自动安装固定版本的本机转码组件，无需配置 AI 或手工填写平台 Token。

扫码是登录账号；监听还需要本项目的连接服务保持运行。关闭工作台浏览器标签或飞书桌面窗口不会主动注销 LarkAgentX；退出 LarkAgentX 登录、凭证失效、停止服务或电脑关机后不能继续监听。QQ 依赖 SnowLuma 对应账号会话保持在线，窗口可以最小化，退出该 QQ 会话会断开连接。工作台、AstrBot、OneBot 和 SnowLuma 使用本机不同端口；`127.0.0.1` 代表本机，不是另一项目的公网 IP。失效临时 AstrBot 路径会在本项目运行目录验证有效后修复，有效自定义路径不会被替换。

多 QQ 账号的规则可使用 `source_account_id` 限定来源 QQ，使用 `target_account_id` 指定发送 QQ。旧规则未指定账号时，只有目标群在已验证在线账号中归属唯一，系统才会自动选择；共有群或多账号私聊需明确选择账号。实时登录身份来自已连接 OneBot 的 `get_login_info`，不是只看 QQ 进程是否存在。飞书桌面进程和 LarkAgentX 账号连接状态分别显示；已有有效凭证时自动恢复监听，无需反复扫码。
